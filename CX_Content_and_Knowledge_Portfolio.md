## 01 | Information Architecture and Governance

### Problem
Content was distributed across multiple technical environments with inconsistent navigation, naming, permissions, ownership, and lifecycle practices. Users could store information, but finding the right place, understanding what belonged there, and knowing how content should be maintained depended too heavily on individual memory.

### My role
Designed the information architecture and authored a **60+ page governance SOP** covering repository structure, taxonomy, navigation, metadata, permissions, naming conventions, lifecycle practices, archival rules, and stewardship. I then translated high-use concepts into diagrams, quick-reference sheets, and one-page guidance.

### Content decisions
- Organized information around enduring work rather than individual preference.
- Defined predictable content patterns so users could recognize where information belonged.
- Made ownership and stewardship visible instead of leaving responsibility implicit.
- Tested terminology and navigation with branch users and revised labels where people lost the path.
- Used progressive disclosure so detailed governance existed without forcing every user to read the full SOP.

### Result
Created a shared operating model for content organization and stewardship across three technical environments, improving consistency, searchability, and maintainability.

## 02 | Role-Based Onboarding and Offboarding Content System

### Problem
Civilian, contractor, and military personnel followed overlapping but nonidentical processes, with responsibilities distributed across multiple offices and additional branches based on entry conditions. A single universal checklist would have forced users to interpret large amounts of irrelevant guidance.

### My role
Created a **six-part onboarding and offboarding content system** containing **230+ role-specific actions**. Mapped phases, owners, prerequisites, dependencies, concurrent work, branching paths, and completion evidence.

### Content decisions
- Split guidance by personnel category and process direction so each reader received the shortest accurate path.
- Preserved consistent terminology and structure across all six guides.
- Identified which actions could occur in parallel and which required upstream completion.
- Documented blocked states and ownership so users knew what was waiting, why, and who could resolve it.
- Structured the content so the same process knowledge could be reused for onboarding, handoff, and support.

### Result
Turned fragmented process knowledge into a repeatable guidance system that was selected for adoption across an entire Headquarters Marine Corps division.

## 03 | Visitor Access Request Workflow Content

### Problem
Visitor requests required accurate routing, role-specific instructions, security-aware processing, status visibility, reminders, and exception handling. A generic confirmation email would not tell users what had actually happened or what they needed to do next.

### My role
Mapped the end-to-end workflow, built the Microsoft Forms / SharePoint Lists / Power Automate solution, and wrote and tested the user-facing and administrator content that supported it.

### Content model
Content changed according to:

- Personnel category
- Security classification
- Workflow state
- Required action
- Request age
- Exception or failure condition

Representative message pattern:

> **Request received:** Your visitor access request was received and recorded as [Request ID]. Current status: [Status]. No further action is required unless additional information is requested. You will receive another update when the request advances or action is needed.

### Content decisions
- Identify the request and current state in every message.
- Explain what changed before giving instructions.
- State explicitly whether action is required.
- Use different messages for received, under review, awaiting action, completed, and exception states.
- Give administrators the affected step and recovery guidance rather than a generic failure notice.

### Result
Paired automation with clear conditional guidance so users could understand the state of their request without relying on informal follow-up.

## 04 | CDRL Submission and Tracking Content

### Problem
A manual deliverable process made identifier control, metadata quality, attachment handling, status visibility, and failure recovery difficult to manage consistently.

### My role
Designed and documented the full submission lifecycle using Microsoft Forms, SharePoint Lists, Teams, and Power Automate. Wrote contributor guidance, confirmation messages, administrator instructions, status language, and recovery content.

### Content decisions
- Used field labels and examples to set expectations before submission.
- Confirmed the assigned report identifier and transaction state after intake.
- Wrote messages around the reader's **next action**: correct, wait, verify, or resubmit.
- Added administrator recovery guidance for partial failures rather than forcing a full restart.
- Preserved traceability by identifying the submission and state in each message.

### Result
Replaced an informal handoff with a guided, trackable process that combined system behavior and content into one controlled user experience.

## 05 | Content Testing and Iteration

My documentation work is usually grounded in direct system use rather than secondhand notes alone.

Examples include:

- Functional, usability, and regression testing for enterprise software
- Formal test plans with expected vs. observed behavior
- Defect and usability findings with reproducible steps
- A 72-hour investigation of a heavily customized ServiceNow environment
- Stakeholder workshops and workflow mapping
- Terminology, navigation, and guidance revisions based on user confusion and observed behavior

My working pattern is simple: **observe the real workflow, reconcile system behavior with stakeholder expectations, explain the actual decision points, and revise until the content supports the task.**
